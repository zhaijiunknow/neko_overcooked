## 1. 这一轮的主线：**"可走性"模型重做**

### 旧模型（错的）

"拿这一格的地板高度和**厨师所在层**比，差 > 阈值就算墙"，阈值反复调
（±2 → 3.0 → 按本关自适应 4.80）。**方向就是错的**，被用户三个反例打死：

| 落差 | 地板性质 | 用户要求 | 为什么阈值做不到 |
|---|---|---|---|
| 2.40 | 静止 | **放** | |
| 1.65 | **会动**(平台沉下去) | **拦** | **1.65 < 2.40，一大一小** |

**大的放行、小的封死 —— 不单调 ⇒ 任何单一阈值必有一头错。**

### 新模型（用户提的，已实现）

**高度是"边"的属性，不是"格"的属性**：

```
step_ok(a, b) = |地板(a) − 地板(b)| ≤ STEP_MAX(0.85)
可达 = 从厨师泛洪, 逐边用 step_ok
传送门 = 额外的边(不是地形)
```

- 有台阶/坡道 → 逐级 ≤0.85 → 泛洪自然爬上去
- 平台沉下去 → 邻格一步差 1.65/7.58 → 进不去 = 洞 ✓
- **"到不到得了"完全交给 BFS**，不再拿阈值猜

**`STEP_MAX = 0.85`**（不是游戏的 `0.65`）：游戏那个是**跨步吸附**的分界，超了只是
"不吸附"；实测能走的台阶是**转梯 0.80、坡道 0.70/0.76**。0.65 会把它们整条判成墙。

### 这一改**作废了一大批东西**（都还在代码里，但**不再是判据**）

`movableFloor`(C# 查组件) · `htol`(自适应容差) · `stand_blocked`/`height_ok`/`at_y` ·
`groundKind`(坡道豁免) · `is_slope()`。
**建议清掉** —— 留着的话下一个人会以为它们还在起作用，然后去调那个数（那条路走过两轮，是死的）。

### 3.1 ✅ 结案：下沉楼梯被判可达 —— **泛洪没错，不是 bug**

用户原话：
> "地平面是 0，下沉楼梯 3 格都下沉到 -7，**你不能因为下沉楼梯三个相邻就判断它可达**"

**实机抓 69 帧 + 离线重放查清了。** 那一块是 `s_wizard_5_5` 的**两条镜像转梯**，
各 3×3 = 9 格，射线打中的是 `Step` / `Step 2` / `Step 4`
（**`layer28 = SlopedGround`，不是 platform** —— 所以"扫移动平台"的思路会漏掉它）。

| | |
|---|---|
| 行为 | **两条反相**：一条升到 `0.38/1.18/1.88`（级差 0.80）时，另一条沉到 `-7.20` |
| 升着的那条 | **就是过河的桥** —— 最低一级 `0.38` 离地面 `0.00` 只差 0.38 ≤ `STEP_MAX` ⇒ 踩得上 ⇒ 爬到顶 ⇒ 过河 |
| 沉着的那条 | 同一跳变成 **7.58**（`STEP_MAX` 注释里那个数就是这个关卡的出处）⇒ 那半边被切断 |
| 结果 | `可达` 在 **42 ↔ 78** 之间摆，而 **`可走` 恒 84、地形一个字没变** |

**用户原话是对的，代码也正是这么做的**：六格内部相邻**不产生**可达性（泛洪只看
"有没有外部的邻居能一步迈进来"），沉下去时两条边界边落差 7.20 / 9.20 都被 `step_ok` 判死。

⚠ **交接包里那句"可走84 = 可达84"没复现**（加了传送门边之后最大 78）。
当初判定"下沉楼梯被算可达"的依据就是这句 —— 它要么来自别的时刻，要么来自别的工具。

**真正的问题在显示层**，见 §3.3。

### 3.2 ✅ `STEP_MAX`：0.85 → 1.00

用户实测指出：西梯在 `1.88/1.31/0.38` 这个角度时，中间那级 `1.31 − 0.38 = **0.93**`
过不去，于是"地面 → 西梯 → 左平台 → 传送门 → 右半边"整条链子断在这一跳上。

两条梯子**反相**、处在转动周期的不同角度，而转梯各级在**竖直方向的投影随角度变**
⇒ 0.93 是那个角度的真实读数，不是测错。

拿 69 帧实机落帧扫过一遍，**`0.95 ~ 1.10` 是一整段平台、行为完全一致**：

- 西梯中间/最高进可达集：**6/7 帧 → 27/28 帧**
- 左平台门 / 右门 / 右半边：**39 帧 → 60 帧**
- **沉下去的那条梯子（东梯）在每一个取值下都纹丝不动（38/68 帧）** ⇒ 没有误放

取 `1.00`（这段平台的中点，给"别的关可能有稍大的台阶"留余量）。
`1.65 / 7.58`（平台沉下去）和各关层间距 `1.56 / 2.35 / 2.40` 都 **> 1.00**，仍然拦得住。

⚠ **只在 `s_wizard_5_5` 上验过** —— 别的关若出现"本来过不去的地方现在判能走"，是它引起的。

### 3.3 ✅ mapview：`V` 一符多义 → 拆开，并新增「可达图」

**症状**：同一张地形、同一份字符网格，图面**一会儿是一大片房间、一会儿只剩个十字**，
看着像"地图没重构"或"哪儿都到不了"。

**根因**：`_mark` 把"**到不了**"也返回 `CH_TOO_LOW = "V"` —— 和真空洞**同一个字符**。
可达集一大一小（实测 42↔78），整张图就换个样子；而 `gridwatch` 打的是原始 `tm.grid`
（不走 `_mark`），于是**同一个房间在两个工具里长得完全不一样**。

**改动**：

- `neko/terrain.py`：新增 `CH_UNREACHED = "-"`，`_mark` 的"到不了"改用它；`V` 只留真空洞/站不下
- `tools/mapview.py`：「地形图」回归**原始**（`ascii()` 不带 reach）；**新增「可达图」一节**；
  两节各有独立图例；`MD_SECTIONS` 加 `可达图`
- `tools/mapview.py`：`--watch` 切片同样出两张图

### 3.4 ⚠ 新发现：传送门端点会**动**，可达随之剧烈摆动

在 `s_wizard_school_3_4` 上实测 39 片：**厨师格一帧没变、地形基本没变，可达却在 27↔87 之间摆**。
定位到唯一输入变化是**传送门边数**（`4 / 6 / 8 / 12` 来回跳）。

md 的「传送门配对」节给出了答案 —— **出口的名字就叫 `Teleport_Moving`**：

```
Teleportal  门(19.20, 8.79) →  **Teleport_Moving** @ (19.70,13.13)
```

⇒ **门是跟着动的**，端点一挪边就重算，可达跟着跳。这条还没做成判据，先记着。

另：`s_rapids_2_1` 上 `'H' ↔ 'x' ↔ 'V'` 频繁互翻、地板在 `0.00 ↔ ?(没地面)` 之间变，
可达在 31~41 走 —— 像是潮水/涨落机制。

## 5. 这一轮踩的坑（最重要的一节）

### 5.1 **先怀疑自己的工具，再怀疑模型**（这一轮至少三次）

| 现象 | 真相 |
|---|---|
| "没有切片输出" | `watch_loop` 里 `movers` **没定义** → 第一片切片就 `NameError`。交接包那句"`--watch` 实机跑通"是**幸存者偏差**（跑的那几次恰好没变）|
| "190 秒跨 3 个周期 0 切片 → 模型看不见限时平台" | 其实**只比了字符网格**，而平台升降**只改高度不改字符**。是**监视器瞎** |
| "水面在 Default 层" | 探针写在 `FloorChar` 里，而 `'H'` 的格子**不走那条路** → 读到的是数组默认值 0。**从没跑过的数据里读出了结论** |

**共同点：工具静默地什么都没做，而输出和"什么都没发生"长得一模一样。**
对策：**心跳**（没输出 = 真的没变）、**"没找的"和"找到了但为空"要分开报**。

### 5.2 **全局 `str.replace` 不带计数会误伤**（这一轮两次）

改 `_mark` 的调用处，把 `ascii_reach` 里那处也改了（那个函数没这个参数）→ `NameError`，
整个 mapview 崩。另一次是 `platforms=plats`。
**改调用处要么带计数、要么用精确编辑。**

### 5.3 **静默反着做**：`SPRAY` → `unspray`

```csharp
switch (action.ToLowerInvariant()) {          // 分派: 小写化
    case "spray": case "unspray":
        return SprayAction(controls, action == "spray");   // 比较: **大小写敏感**
```

⇒ 任何非全小写都会**静默变成"停喷"**，而且返回 `ok:true`。
而引擎一直发的是大写（为了绕开早就改名的诊断命令）⇒ **`Engine.extinguish()` 从来没喷过**。
**这类 bug 最难的地方：它报成功。**

### 5.4 **别拿自己推的坐标去质疑地形**（上一轮记过，这轮又犯）

用 `origin + idx*size` 猜网格世界坐标 → 得出"漏 23 格"的假结论。
**判据要用可信的**：台面落在 `'#'` 上的比例、`可走 N` vs `可达 M`。

### 5.5 **"够不着"/"不相交"不一定是 bug**（用户强调）

用户原话："**不相交的时候又可能是地图设计的，如果有明显错误我会和你说**"。
分厨房/上下层是设计，解法是**传接球**，不是修地形。**先当观察报出来，等他指。**

### 5.6 **别执着于调阈值**

三个反例（1.65 要拦、2.40 要放、0.80 要走）说明了：**判据本身不成立**时，
再怎么调都是在错的维度上努力。**换判据（格→边）比调数有效一个数量级。**

### 5.7 `.NET 2.0` 的 mscorlib 里**没有 `Func<>`**

本项目 `-nostdlib+` 显式引 v2.0 的 mscorlib ⇒ lambda/`Func<>` 直接 `CS0246`。
**小工具一律写成私有方法**。

### 5.8 **筛选/过滤是静默失败的高发区**（这一轮又中两次）

| 现象 | 真相 |
|---|---|
| 桌面 md 里**一片变化都没有**，看着像"监视器没输出" | watch 的标签从 `变化切片` 改成了 `可达变化`，**`MD_SECTIONS` 白名单没跟着改** —— `to_markdown` 是按标题**子串**筛的，每一片全被过滤掉 |
| md 整个文件不存在，终端一声不吭 | `_flush_md` 的 `except Exception: pass` —— **"写失败"和"没东西可写"输出一模一样** |

两个都是 **§5.1 那条**的变体：**工具静默地什么都没做**。
对策也一样 —— **改标签/加分类，必须同时看白名单**；**异常别吞，至少喊一声**（现在失败会打 `[md] ⚠ 写不进去`）。

### 5.9 **"看起来像 A，其实是 B"要先问"还有没有第三个输入"**

排查"可达为什么变"时，连着错了两次：
1. 先归咎**地形**（只比了地板高度，漏了**网格字符** —— 而 `teleport_edges` 只看字符）
2. 补上字符后，剩下的帧归咎**厨师位置** —— 实测 39 片里**厨师格一帧没变**，真正在变的是**传送门边数**

**教训**：一个量变了，先把它**所有输入**列出来逐个比（这里是 地形/厨师/传送门），
比不出来再喊"对不上" —— 现在 watch 会这么做，四项都没变时主动打 `⚠⚠ …要查`。

### 5.10 ★ **"参数没穿进来"会写成必然崩的代码，而静态检查常常看不见**

`_stand_cell` / `_stand_cells`（`neko/engine.py:807` / `:845`）里用了 `st` 和 `km`，
而它们**既不是参数、也不是局部变量**——函数体第一件事就是 `self.chef_y(st)`，
必然 `NameError`。四个调用点（`_approach`:962、`_grab_from_belt`:1266、传送带兜底:1346、
`navigate_smart` 的障碍目标分支:1711）**没有一个 try 兜着** ⇒
**整个"走到台面旁边"的路径全瘫**，引擎根本跑不起来。

成因像 §5.2：`at_y=self.chef_y(st)` / `extra_edges=teleport_edges(km, tm)` 是后加的，
**参数没跟着穿进来**；而 `teleport_edges` 也**没加进 import**。（已在 §4.2 一并修好。）

**为什么一直没暴露**：这一轮全在用 `mapview` / `gridwatch`，**没跑过引擎**。

**对策**：做了个 AST 级的裸名字扫描 —— 判据是"一个 `Name` 以 Load 出现，
而它在 参数/局部/闭包/模块全局/内置 里**都找不到** ⇒ 运行时必炸"。
全仓库 22 个 `.py` 扫完，**只有 `engine.py` 这两处**。

⚠ 它和 ruff/pyflakes 是**互补**的：**函数内局部导入过的同名**会让那些工具看不见（已知盲区，
见 `check-names-blind-spot` 那条备忘），而这个判据更死板、专抓"必然崩"。
